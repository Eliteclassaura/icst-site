## ADR-026 — OGCS and Search Evidence integrate through versioned contracts and a scoped service account, not shared code or databases

**Status:** Proposed · 2026-09-05 · Owner decision recorded: OGCS is the owner's private control system, not a client-distributed product

**Context.** The owner is building OGCS (Organic Growth Control System): a single controller agent that observes SEO evidence across every client site, decides what to change, executes or routes the work, verifies it, and reports. Evidence comes from the Search Evidence Suite — a browser-only, IndexedDB-backed app with no server API whose only machine-readable surface is its exports (`search-evidence-console/project` v1, `search-evidence-suite/snapshot` v1, xlsx, csv). OGCS today is a specification (`OGCS_SYSTEM_SPEC_v1`, JSON Schema, playbook seed) with no code. The first pilot is the H2O Cooling WordPress → Payload migration. The Factory must decide where OGCS lives and how it may touch client sites.

The Factory's existing invariants that bear on this: one Next + Payload process, one Postgres, one bucket, one secret set per client with no `clientId` multi-tenancy (ADR-004, ADR-005); jobs only in the separate worker with the outbox idempotency pattern (ADR-017, `src/jobs/sendMockEmail.ts`); the blueprint as the only content ingress (ADR-025); design-contract as the model for adapters (one versioned intermediate, provenance per value, reproducibility gate — ADR-006/ADR-020); no `search-*` code in starter or client images until licensing is settled (ADR-023); Search Evidence characterised before extracted, local-first stays a product mode (ADR-010); exact version pinning enforced in CI (`tools/scripts/check-versions.mjs`).

**Decision.**

1. **OGCS is a separate system.** Own repository, own Postgres, own scheduler, own artefact store, own secrets. It is deployed once for the agency, never per client, and never ships in a client image or starter. It depends on the Factory only through the npm package `@factory/seo-contracts`.
2. **Search Evidence Suite is unchanged and independent.** Its `*.seoproject.json` export is the evidence source. An adapter (`ses-to-evidence`, living in the OGCS repo, tested against `docs/baselines/ses-fixtures/`) turns it into the `evidence-bundle` contract. A native export may be added to the suite later; the adapter then becomes a byte-identical no-op.
3. **The Factory gains one dependency-free package: `packages/seo-contracts`.** Zod schemas, TypeScript types, golden fixtures and a `validate` CLI for five contracts: `blueprint` v2, `evidence-bundle`, `page-decisions`, `qa-report`, `deploy-event`. Depends on `zod` only; an ESLint `no-restricted-imports` rule forbids it importing `agency-core` and forbids `agency-core` importing it.
4. **Two publishing lanes, both audited.**
   - **Lane A — structural, via blueprint.** URL creation/removal, redirects, IA changes, collection changes, anything produced by a PRUNE / REDIRECT / CONSOLIDATE / NOINDEX decision. OGCS emits `page-decisions`; `tools/wordpress-import` (or a future `tools/decisions-apply`) turns it into a blueprint diff; seed applies it; the parity gate must pass before deploy. Git is the review surface.
   - **Lane B — content, via a scoped service account.** Title, meta description, body copy, internal links, image ALT, new articles/posts, schema data on an existing page — the playbook's green tactics. OGCS writes through Payload's REST API using an API key belonging to a `service-accounts` document with the single role `automation`. The account can create/update `pages`, `posts`, `media`, `redirects` and read what editors can read; it cannot touch `users`, `service-accounts`, CRM collections, `integrations`, or `audit-log`, and cannot delete anything. Every write is recorded by the existing audit hook with the service account as actor. The key is per client, stored only in OGCS's env, revocable in the client's admin.
   - What Lane B may not do: change a slug (that is a redirect — Lane A), publish a page whose `verification.status` is not `verified` (enforced by a `beforeChange` hook), or set `noindex` on a page with `seo.lock = true`.
5. **QA results and deploy events flow back as contracts.** `tools/parity/compare.mjs` wraps its report as `qa-report`; the app emits `deploy-event` on deploy. In v1 these are files committed under `apps/<client>/handoff/`; in v2 they travel as HMAC-signed webhooks through a new `emitWebhook` job using the outbox idempotency pattern, with the retry/dead-letter schedule already designed in `docs/crm-sync.md`.
6. **Payload plugin is optional and flag-gated.** `packages/payload-search-plugin` (editor side-panel showing the current decision and evidence hint for the page being edited; read-only `page-decisions` and `qa-reports` reference collections) registers only when `integrations.searchIntelligence.enabled` is true. Off in all starters and client images by default (ADR-023 preserved).
7. **Blueprint becomes v2 and gets a schema.** Adds `pages[].migration` provenance group, `pages[].decision_ref`, explicit `parity` block; `redirects[]` are seeded; `seed.ts` validates before writing.

**Consequences.**

- Five Factory prerequisites are pulled forward because H2O needs them regardless of OGCS: redirects served by `proxy.ts` and seeded from the blueprint (today written but never read); blueprint schema; `migration` group on pages; `verification.status` enforced at publish; a WordPress importer. See `docs/factory-prerequisites.md`.
- New auth collection `service-accounts` (`auth: { useAPIKey: true, disableLocalStrategy: true }`), new role `automation`, new role group `AUTOMATION_WRITERS`; the threat-model matrix gains a row and the "system-only create" set gains `service-accounts` (admins only). `SENSITIVE_COLLECTIONS` gains `service-accounts`.
- `integrations.searchIntelligence` gains `ogcsProjectId`, `ogcsBaseUrl` (public identifiers); `OGCS_WEBHOOK_SECRET` is env-only with a fail-closed readiness check like `turnstileReadiness()`.
- OGCS holds exactly one credential per client site (the Lane-B API key) and nothing else from the Factory; it never receives `DATABASE_URI`, `PAYLOAD_SECRET` or S3 credentials.
- Rollback: Lane A by `git revert` + re-seed; Lane B by Payload document versions (`maxPerDoc 50`) or by OGCS re-applying the previous value from its own change-set record; both lanes leave audit rows; the service account can be disabled per client in one click.
- Rejected: embedding OGCS in the monorepo (contradicts ADR-005, multiplies blast radius, forces OGCS tables into every client's migrations); OGCS with direct Postgres or local-API access; a message broker (Payload's Postgres queue + outbox suffices, ADR-004/ADR-014); extracting the Search Evidence engine for this pilot (ADR-023 blocks shipping it and H2O needs exports, not the engine).

**Tests required before Accepted.** Contract fixtures validate and negative fixtures fail with the expected path; `ses-to-evidence` reproduces a golden `evidence-bundle` from `ses-fixtures/`; importer golden test from a small WordPress SQL fixture; e2e: every `page-decisions.redirects[]` row resolves in one hop; threat-model: `automation` row across all sensitive collections, service account cannot escalate, delete, or read CRM; `verification` publish gate; parity on syed.ai remains 20/20 after the agency-core changes.

**Not proven here.** OGCS's own runtime (Sprints 1–10 of `OGCS_NEXT_BUILD_STEPS_v1`); webhook transport (v2); the plugin UI; licensing terms that would allow `search-*` code in client images.
